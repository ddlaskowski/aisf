# AI Software Factory v1.5 Safe Patch Engine

## What Changed

v1.5 adds the first Safe Patch Engine layer to AI Software Factory. The engine validates small patch operations before they are written to disk, reports whether the patch was applied or skipped, and exposes deterministic confidence metadata to the retry and scenario-test systems.

This release does not replace the whole editing pipeline. Existing legacy patch behavior remains supported, and only Safe Patch Engine compatible operations are routed through the new engine directly.

## Why The Patch Engine Was Needed

Earlier versions could apply AI or deterministic patches using simple string replacement and fallback append behavior. That was useful for speed, but risky in edge cases:

- Duplicate declarations could be introduced accidentally.
- Patch anchors could match multiple places.
- Import or require statements could be appended below executable code.
- A skipped or no-op patch could still look like an applied change to retry control.

The Safe Patch Engine gives the system a small deterministic safety layer before edits reach the filesystem.

## Architecture Overview

The v1.5 patch layer lives in:

```text
src/patchEngine/
  patchTypes.ts
  patchResult.ts
  analyzeFileStructure.ts
  validatePatch.ts
  applySafePatch.ts
  index.ts
```

Runtime integration is intentionally narrow:

- `fileEditor.ts` detects Safe Patch Engine compatible patch operations.
- Safe patches are sent to `applySafePatch(...)`.
- Unsafe patches are skipped with a reason.
- Legacy patches continue through the existing path.
- Legacy append fallback is guarded by `appendSafe`.
- `runTask.ts` counts effective changes from actual file operation results instead of proposed operation count.

## Patch Operation Types

### replace

Replaces one exact target with replacement text.

```json
{
  "type": "replace",
  "target": {
    "type": "exact",
    "match": "console.log(testVar);"
  },
  "replacement": "console.log(typeof testVar !== \"undefined\" ? testVar : undefined);"
}
```

Legacy compatible string replace is also recognized:

```json
{
  "type": "replace",
  "target": "testVar",
  "content": "safeValue"
}
```

### insertAfter

Inserts content after a unique anchor.

```json
{
  "type": "insertAfter",
  "anchor": {
    "text": "console.log(\"ready\");"
  },
  "content": "\nconsole.log(\"done\");"
}
```

### appendSafe

Appends normal executable code only when the content passes safety checks.

```json
{
  "type": "appendSafe",
  "content": "console.log(\"done\");"
}
```

## Safety Rules

The engine validates patches with simple deterministic heuristics:

- Replacement targets must exist.
- Replacement targets must be unique.
- Insert anchors must exist.
- Insert anchors must be unique.
- Patch content must not introduce duplicate declarations.
- `appendSafe` blocks import or require content.
- Import or require insertion after executable code is blocked.
- Empty patch content is rejected for insert and append operations.

The engine deliberately does not use a full AST parser yet. It detects declarations with simple line-based patterns such as:

```text
const name =
let name =
var name =
function name(
```

## Metadata Fields

`fileEditor.ts` now returns operation metadata so orchestration and retry control can distinguish a real edit from a skipped patch.

```ts
{
  changed: boolean;
  patchEngineUsed: boolean;
  patchSkipped: boolean;
  patchSkipReason?: string;
  patchChanged: boolean;
  patchConfidence?: "high" | "medium" | "low";
}
```

Meaning:

- `changed`: a file was effectively changed.
- `patchEngineUsed`: the Safe Patch Engine evaluated the patch.
- `patchSkipped`: the Safe Patch Engine rejected the patch.
- `patchSkipReason`: human-readable reason for a skip.
- `patchChanged`: the Safe Patch Engine produced a changed file.
- `patchConfidence`: deterministic confidence score from validation.

Retry control can now treat `patchChanged: false` and `changed: false` as no effective change.

## Confidence Scoring

Confidence is deterministic and validation-based. It is not AI confidence.

### High

Assigned when:

- Exact replace target exists once.
- Insert anchor exists once.
- No duplicate declarations are detected.
- No import or require placement risk is detected.

### Medium

Assigned when:

- `appendSafe` appends normal executable code.
- No duplicate declarations are detected.
- No import or require placement risk is detected.

### Low

Assigned when validation rejects a patch, including:

- Missing anchor.
- Ambiguous anchor.
- Duplicate declaration.
- Import or require below executable code.
- Empty patch content.

## Test Coverage

The scenario runner includes deterministic Safe Patch Engine checks without adding a test framework.

Covered cases:

- Safe replace removes a duplicate declaration line.
- Duplicate declaration insertion is blocked.
- Unsafe import or require append is blocked.
- Ambiguous anchor is blocked.
- Normal `appendSafe` code is applied.
- Safe replacement fixer emits an exact Safe Patch Engine replace patch.
- Guarded legacy append exposes Safe Patch Engine skip metadata.
- Patch expectation assertions support:
  - `engineUsed`
  - `skipped`
  - `changed`
  - `confidence`
  - `skipReasonIncludes`

Final v1.5 hardening checks:

- `safe-patch-duplicate-blocked`
- `safe-patch-ambiguous-anchor-blocked`
- `safe-patch-exact-replace-applied`
- `safe-patch-append-normal-code`

## Known Limitation

The `retry-stop` end-to-end scenario remains unstable and observational. AI may solve or alter the controlled failure before the retry-stop artifact appears. The deterministic retry-control unit remains the stable assertion for retry stop behavior.

In this local Windows sandbox, end-to-end CLI scenarios may be skipped by the harness when `spawnSync node.exe` returns `EPERM`. The deterministic unit checks still run and pass.
